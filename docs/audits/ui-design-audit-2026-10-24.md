# ممیزی طراحی و هماهنگی رابط سیستم

تاریخ: ۲۴ اکتبر ۲۰۲۶ — checkout در زمان بررسی: `2eefe37`.

این سند snapshot ممیزی قبل از اصلاح است. نتیجهٔ تغییرات و اعتبارسنجی بعدی در [گزارش یکپارچه‌سازی](ui-design-unification-2026-10-24.md) ثبت شده است.

## دامنه و اعتبار نتیجه

این گزارش **ممیزی کد و قراردادهای طراحی** است. ۴۶۹ فایل Razor شامل ۳۳۵ فایل غیرpartial و ۱۳۴ فایل partial/layout، در ۹۰ پوشهٔ ماژول به‌علاوهٔ Shared و دو فایل ریشه، فهرست‌برداری و با قواعد ساختاری جستجو شدند. ۴۲ فایل CSS در `wwwroot/css/ptg`، ترتیب assets در دو layout، تعریف bundle در csproj و اسکریپت‌های مشترک مرتبط بررسی شدند. بررسی دستی روی ریشه‌های مشترک و نمونه‌های مشخص زیر انجام شد؛ فهرست‌برداری همهٔ فایل‌ها به معنی خواندن دستی تک‌تک صفحات نیست.

**تأیید بصری همهٔ صفحات انجام نشده است.** مرورگر متصل و نشست واردشده در دسترس نبود. هیچ screenshot، اندازه‌گیری DOM زنده، تست ارسال فرم، اجرای export یا آزمون screen reader مبنای این گزارش نیست. موارد قطعی زیر از کد فعلی اثبات می‌شوند؛ شدت اثر بصری و موارد وابسته به runtime جدا مشخص شده‌اند. نتیجه، گواهی کامل‌بودن بررسی تمام حالت‌های سیستم نیست.

هیچ کد برنامه، CSS، مسیر، مجوز، مدل یا داده‌ای تغییر نکرد. خروجی فقط گزارش و فهرست پوشش است. Build و تست .NET اجرا نشد؛ ممیزی خواندنی به ساخت برنامه نیاز نداشت.

فایل‌های همراه:

- `ui-design-coverage-2026-10-24.csv`: یک ردیف برای هر فایل Razor؛ نام ماژول، نوع صفحه و استفادهٔ مستقیم از primitives مشترک.
- `ui-design-modules-2026-10-24.md`: پوشش ۹۰ ماژول و Shared و شمارش ساختاری.

همهٔ مسیرهای شواهد زیر نسبت به ریشهٔ repository هستند. شمارهٔ خط مربوط به snapshot زمان ممیزی است.

## نتیجهٔ اصلی

سیستم از کامپوننت‌های مشترک قابل‌استفاده برخوردار است؛ مشکل اصلی نبود کامپوننت نیست. **مالکیت ظاهر بین توکن‌های پایه، لایه‌های اصلاحی، CSS مخصوص ماژول، دو layout و JavaScript تغییر‌دهندهٔ DOM تقسیم شده است.** نتیجه، چند مسیر متفاوت برای نمایش یک فرم یا جدول و چند قرارداد متناقض برای یک کامپوننت است.

وجود لایهٔ نهایی Mashal به‌خودی‌خود اشکال نیست؛ در کد و قرارداد پروژه عمداً انتخاب شده است. ایرادهایی که در ادامه آمده‌اند جایی هستند که این قرارداد واقعاً اعمال نمی‌شود، با قواعد قوی‌تر قبلی شکست می‌خورد، یا در مسیرهای مختلف یکسان بارگذاری نمی‌شود. تعداد فایل یا تعداد `!important` به‌تنهایی اثبات باگ نیست.

## یافته‌های تأییدشده در کد

اولویت «بالا» یعنی اصلاح مقدم بر پرداخت بصری؛ «متوسط» یعنی ناهماهنگی یا مسئلهٔ دسترس‌پذیری/نگهداری مهم. خطای بحرانی مالی یا دستکاری داده در این ممیزی اثبات نشده است.

### D01 — استایل انتقال مشتری در ورود مستقیم و SPA یک قرارداد ندارد — بالا

- **شاهد:** `Views/CustomerToCustomerPayments/Create.cshtml:9–10` فایل `82-customer-transfer.css` را بدون `data-ptg-page-asset` وارد می‌کند. `wwwroot/js/spa-nav.js:569–570` فقط stylesheetهای دارای همین marker را preload می‌کند و `:610–641` نیز فقط assets نشان‌گذاری‌شده را هماهنگ می‌کند.
- **ریشه:** CSS اختصاصی صفحه خارج از چرخهٔ assets ناوبری SPA قرار گرفته است؛ این فایل در bundle عمومی هم reference ندارد.
- **اثر:** بازکردن مستقیم و ورود از لینک داخلی می‌توانند دو ظاهر متفاوت تولید کنند. ورود SPA از صفحه‌ای که این CSS را ندارد، stylesheet را از این قرارداد دریافت نمی‌کند؛ ورود مستقیم نیز ممکن است stylesheet بدون مدیریت پاک‌سازی باقی بگذارد.
- **مرز اصلاح:** ثبت stylesheet در قرارداد موجود page asset؛ سپس مقایسهٔ ورود مستقیم، ورود SPA، خروج از صفحه و بازگشت. خاموش‌کردن کلی SPA راه‌حل این مشکل نیست.

### D02 — صفحهٔ ثبت و ویرایش انتقال مشتری یک partial ولی assets متفاوت دارند — بالا

- **شاهد:** `Views/CustomerToCustomerPayments/Create.cshtml:9–39` هم CSS و هم initializer اختصاصی را دارد؛ `Views/CustomerToCustomerPayments/Edit.cshtml:7–12` همان `_CreateForm` را استفاده می‌کند اما فقط validation scripts می‌آورد.
- **ریشه:** مالکیت CSS و تعاملات partial در صفحهٔ Create مانده است.
- **اثر:** در بازکردن مستقیم Edit، کلاس‌های `ctc-*` فایل اختصاصی خود را ندارند. listener دکمه‌های «حذف» انتخاب مشتری و همگام‌سازی نمایش مبلغ/ارز نیز در Edit از این مسیر ثبت نمی‌شوند.
- **مرز اصلاح:** assets و initializer مشترک برای مصرف‌کننده‌های Create/Edit، با lifecycle تکرارپذیر. نام فیلدها و payload دست نخورند.

### D03 — نمایش نام مشتری با انتخاب جدید همگام نمی‌شود — بالا

- **شاهد:** `Views/CustomerToCustomerPayments/_CreateForm.cshtml:43–44` و `:84–85` نام را یک‌بار از navigation property مدل در input readonly می‌گذارند؛ متن placeholder وعدهٔ نمایش پس از انتخاب می‌دهد. initializer در `Create.cshtml:17–39` فقط مبلغ، ارز و clear را مدیریت می‌کند. جستجوی شناسه‌های این دو input در JS مشترک، handler دیگری نشان نداد.
- **ریشه:** نمایش مشتق‌شده از انتخاب، فقط server-render شده و مسیر update ندارد.
- **اثر:** در Create می‌تواند خالی بماند و در Edit پس از تغییر مشتری نام قبلی را نشان دهد. این یافته دربارهٔ نمایش است؛ خطای ثبت شناسه یا حسابداری از آن نتیجه‌گیری نشده است.
- **مرز اصلاح:** نمایش نام و clear آن از همان select موجود تغذیه شود؛ انتخاب و نام نمایشی با ماوس، کیبورد و خطای اعتبارسنجی تطبیق داده شوند.

### D04 — سند مودال با صفحهٔ کامل از یک قرارداد بصری استفاده نمی‌کند — بالا

- **شاهد:** `Views/_ViewStart.cshtml:2–4` با `modal=1` به `_ModalLayout` می‌رود. `_Layout.cshtml:478–485` لایه‌های `76-form-system.css` و `78-mashal-reference.css` را بارگذاری می‌کند و `:504` کلاس `mashal-ui` دارد. `_ModalLayout.cshtml:87–101` تا لایهٔ Details می‌رود، اما این دو فایل را ندارد؛ body آن در `:120` نیز `mashal-ui` ندارد.
- **ریشه:** دو فهرست مستقل assets و دو مجموعهٔ کلاس زمینه. `core.js` برای page modal از iframe استفاده می‌کند؛ CSS سند والد به iframe ارث نمی‌رسد.
- **اثر:** یک فرم در صفحهٔ کامل و `?modal=1` از قواعد متفاوت ارتفاع کنترل، فاصله، رنگ و سطح استفاده می‌کند. حتی افزودن stylesheet نهایی بدون اصلاح scope به‌تنهایی کافی نیست؛ بسیاری از selectorها به `#ptg-main-content` وابسته‌اند که در سند مودال وجود ندارد.
- **مرز اصلاح:** استخراج قرارداد مشترک محتوای فرم از chrome پوسته؛ حذف عمومی همهٔ تفاوت‌های layout توصیه نمی‌شود. نبود loader/header/sidebar در سند مودال به‌خودی‌خود ایراد نیست.

### D05 — دکمه‌های اصلی به دو رنگ اجرایی متفاوت وابسته‌اند — متوسط

- **شاهد:** `45-akaunting.css:203–214` رنگ `.ak-primary-action` را با `!important` از `--ptg-btn-primary` می‌گیرد؛ مقدار پایه در `01-tokens.css:195` برابر `#1062D0` است. `78-mashal-reference.css:12` رنگ `--mashal-primary` را `#2d60c9` تعریف می‌کند و `:221–222` آن را بدون `!important` به `.btn-primary`، `.ak-primary-action` و `.ak-save` می‌دهد.
- **ریشه:** نقش یکسان primary با دو token و دو قدرت cascade کنترل می‌شود؛ لایهٔ نهایی `--ptg-btn-primary` را بازتعریف نمی‌کند.
- **اثر:** دکمهٔ header با `.ak-primary-action` رنگ قدیمی را حفظ می‌کند، درحالی‌که `.ak-save` و برخی `.btn-primary`ها می‌توانند رنگ Mashal بگیرند. hover نیز دو منبع دارد.
- **مرز اصلاح:** یک نگاشت رسمی برای primary action و حذف فقط override اثبات‌شده، پس از بررسی همهٔ stateها. صرفاً افزودن `!important` جدید مشکل مالکیت را ادامه می‌دهد.

### D06 — اندازه و وزن سرستون‌های جدول برخلاف لایهٔ نهایی باقی می‌ماند — متوسط

- **شاهد:** `71-typography.css:130–138` اندازه و وزن سرستون را با `!important` از token می‌گیرد؛ `01-tokens.css:128` برابر `16px/700` است. `78-mashal-reference.css:237–238` برای جدول `14px/500` و `:277` برای جدول قابل‌ویرایش `13px/400` درخواست می‌کند، بدون `!important`.
- **ریشه:** لایهٔ typography هم اندازه و هم استایل کامپوننت را با اولویت بالا مالک شده است؛ لایهٔ reference این مالکیت را لحاظ نکرده است.
- **اثر:** در desktop، تغییر اعلام‌شدهٔ سرستون به ۱۴ یا ۱۳ پیکسل اجرا نمی‌شود. اعداد دارای `.ak-num` نیز در `71-typography.css:170–172` اندازهٔ ۱۶ پیکسل اجباری دارند؛ متن و رقم با مقیاس‌های متفاوت کنار هم می‌افتند.
- **مرز اصلاح:** تعریف یک مقیاس مصوب برای data table و editable table؛ سپس حذف تعارض، با حفظ جداسازی LTR اعداد. این یافته پیشنهاد کوچک‌کردن خودکار فونت نیست.

### D07 — پیام هشدار و موفقیت در محتوای صفحه رنگ اطلاع عمومی می‌گیرند — متوسط

- **مرز اصلاح:** mapping صریح info/success/warning/danger در مالک مشترک؛ بررسی متن و آیکون همراه. این نتیجه به flashهایی که بیرون از main هستند تعمیم داده نشده است.

### D08 — دو موتور متفاوت برای فیلتر جدول فعال‌اند — متوسط

- **شاهد:** قرارداد `docs/UI-DESIGN-SYSTEM.md` جستجو/فیلتر را server-side، با مالک `_AkSearchFilter` و query string معرفی می‌کند. `_Layout.cshtml:850–851` هم `list-grid.js` و هم `ak-search-filter.js` را بارگذاری می‌کند. `list-grid.js:65–83` فیلترهای ستونی می‌سازد و `:96–111` ردیف‌ها را در مرورگر مخفی می‌کند.
- **ریشه:** قابلیت جدید grid بدون به‌روزرسانی قرارداد مالکیت search/filter اضافه شده است. تست ساختاری `ShellViewStructureTests.cs:517–536` عمداً همین رفتار محلی را تأیید می‌کند؛ این کد تصادفاً بلااستفاده نیست.
- **اثر:** دو مدل ذهنی برای فیلتر وجود دارد: فیلتر server با query/chip و فیلتر ستون با state فقط در DOM. export، reload و لینک قابل‌اشتراک، state دومی را از این مسیر دریافت نمی‌کنند. پس نباید به کاربر یک نتیجهٔ واحد و قابل‌اشتراک القا شود.
- **نکتهٔ محافظتی:** `hasMorePages` در `list-grid.js:228–230` برای جدول server-paged دارای pagination، فیلتر و sort محلی را خاموش می‌کند. ادعای «همهٔ فیلترها فقط صفحهٔ جاری را جستجو می‌کنند» نادرست است.
- **مرز اصلاح:** تصمیم محصول دربارهٔ وجود هر دو قابلیت، سپس نام‌گذاری و نمایش scope و هماهنگی مستندات/export. حذف کورکورانهٔ engine توصیه نمی‌شود.

### D09 — فیلتر ستونی فعال می‌تواند در موبایل پنهان بماند — بالا

- **شاهد:** `78-mashal-reference.css:268–269` در عرض زیر ۷۶۸ پیکسل کل `tr.ak-filter-row` را مخفی می‌کند. `list-grid.js:96–111` state و پنهان‌سازی ردیف را نگه می‌دارد و listener برای resize/پاک‌کردن این state ندارد.
- **ریشه:** responsive فقط کنترل را مخفی کرده است، بدون انتقال state یا راه clear.
- **اثر:** بعد از اعمال فیلتر روی عرض بزرگ و باریک‌کردن پنجره، ردیف‌ها همچنان فیلتر می‌مانند اما کنترل ایجادکنندهٔ محدودیت دیده نمی‌شود. نبود chip مشترک، تشخیص علت کم‌شدن داده را دشوار می‌کند.
- **مرز اصلاح:** نمایش وضعیت و clear در موبایل یا انتقال همان فیلتر به UI موبایل؛ دادهٔ کاربر خودکار پاک نشود مگر قرارداد آن روشن باشد.

### D10 — نقش دسترس‌پذیری popover فیلتر با محتوای آن سازگار نیست — متوسط

- **شاهد:** `_AkSearchFilter.cshtml:124` نقش `listbox` دارد، اما `ak-search-filter.js:191–207` لیست button می‌سازد و `:268–275` در حالت متن input و Apply داخل همان ظرف قرار می‌دهد. در این فایل نگاشت `role=option`، `aria-activedescendant`، `aria-controls` و مدیریت Arrow برای الگوی listbox وجود ندارد.
- **ریشه:** یک ظرف چندحالته با semantics یک لیست انتخاب ساده معرفی شده است.
- **اثر:** نام‌گذاری اعلام‌شده برای فناوری کمکی با تعامل واقعی مطابقت ندارد. buttonها با Tab قابل‌دسترسی‌اند؛ ادعای «فیلتر کلاً با کیبورد کار نمی‌کند» مطرح نیست. کیفیت اعلام screen reader هنوز باید آزمایش شود.
- **مرز اصلاح:** انتخاب الگوی درست برای popover چندمرحله‌ای، رابطهٔ کنترل/ظرف، state باز/بسته و بازگشت focus؛ سپس آزمون واقعی کیبورد و screen reader.

### D11 — جهت صفحه در ۸۶ فایل به RTL ثابت قفل شده است — متوسط، مربوط به حالت انگلیسی

- **شاهد:** اسکن attribute دقیق `dir="rtl"` در ۸۶ فایل Razor؛ فهرست هر فایل در CSV آمده است. نمونه‌ها: `Views/Customers/Details.cshtml:122`، `Views/Payments/Details.cshtml:103` و `Views/CustomerToCustomerPayments/_CreateForm.cshtml:6`. پوسته در `_Layout.cshtml:504` براساس زبان RTL/LTR انتخاب می‌کند.
- **ریشه:** جهت در صفحه/partial تکرار شده و از language context جدا شده است.
- **اثر:** حالت فارسی الزاماً خراب نیست؛ در حالت انگلیسی محتوای بعضی صفحات با chrome انگلیسی هم‌جهت نمی‌شود. `direction:rtl` در `82-customer-transfer.css:63` نیز این مسیر را تقویت می‌کند.
- **مرز اصلاح:** جهت محتوای صفحه از زبان جاری، جهت عدد/کد به‌صورت مستقل LTR. این ۸۶ مورد نامزد بررسی معنایی هستند؛ همهٔ RTLهای موضعی لزوماً خطا نیستند.

## دو مورد جانبی در قرارداد فرم

`Dispatch/CreateSaleFromDirectDispatch.cshtml:23` و فرم `ThreeWaySettlement/Index.cshtml:238` در markup خود `@Html.AntiForgeryToken()` صریح ندارند. در دومی `@Html.FormToken()` هست، اما `Helpers/FormTokenHtmlHelper.cs:16–21` فقط `__FormToken` برای idempotency تولید می‌کند؛ این دو token یک نقش ندارند.

این دو فرم با قرارداد صریح repository ناسازگارند. **خطای ۴۰۰ یا آسیب‌پذیری runtime از این مشاهده اثبات نشده است**؛ Razor FormTagHelper فعال است و باید HTML رندرشده و تنظیمات اجرایی بررسی شود. هیچ حفاظت سمت سرور تغییر نکرده است. بررسی کامل امنیت و مجوز خارج از دامنهٔ این ممیزی طراحی است.

## مواردی که سالم یا عمدی بودند

- `_AkSearchFilter`، `_AkPageHeader`، `_AkFooterActions` و خانوادهٔ Details واقعاً مشترک‌اند؛ نبود مصرف مستقیم در یک View ممکن است به دلیل shell/partial واسط باشد.
- برای اعداد قواعد LTR، tabular و isolate وجود دارد؛ مشکل عمومی «همهٔ اعداد RTL هستند» تأیید نشد.
- برای row actions پشتیبانی `:focus-within`، Escape و touch وجود دارد. برخی dropdownهای دارای فرم عمداً از تبدیل به toolbar خارج شده‌اند.
- فیلتر محلی grid برای server-paged دارای pagination مهار شده است؛ این safeguard نادیده گرفته نشده است.
- در اسکن CSSهای غیرbundle، reference بدون fallback به custom property کاملاً تعریف‌نشده پیدا نشد. این بررسی وجود تعریف را می‌سنجد، نه معتبر بودن scope هر تعریف را.
- در اسکن Razor، style block زنده پیدا نشد. فقط ۸ فایل attribute واقعی inline style داشتند؛ از جمله progress، عرض ستون چاپ و visibility وابسته به state. این موارد خودکار باگ محسوب نشدند.
- صفحات سند چاپ، login و workflow گروهی الزاماً نباید هندسهٔ یکسان داشته باشند. تفاوتی که نقش کاری روشن دارد با ناهماهنگی اشتباه گرفته نشده است.
